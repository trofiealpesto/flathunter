# Deterministic rental rules correction — 2026-09-22

The backend now distinguishes affirmative restrictions from negated, historical,
incidental and conflicting text. A numeric match cannot bypass configured natural-
language requirements. This change uses the existing semantic classifier; no local
model or Qwen integration is added.

## Behavior

- `Kein WBS erforderlich`, `not an apartment swap` and `kein WG-Zimmer` no longer
  produce blocking flags or their ranking penalties. Negation is considered within
  each clause; a separate affirmative condition can still reject the listing.
- WBS needs an affirmative requirement or a WBS-specific housing designation.
  Merely mentioning WBS, a neighbouring flat or a question about the permit is not
  sufficient. Shared-flat/roommate mentions alone do not establish a room-only offer.
- Plain `Untermiete`/`sublet` does not establish a fixed end date. Explicit temporary
  language, inflected `befristet` and `fixed-term` remain restrictions.
- Opposing statements, including title/description conflicts and simultaneous
  permanent/temporary signals, defer text rejection to semantic review. Clearly
  disqualifying numeric facts still reject, using the unchanged numeric thresholds.
- `MATCH` from numbers alone is available only for searches whose `mustMatch`,
  `avoid` and `notes` are all empty. Configured free-text preferences require the
  existing semantic evaluation/cache. An unavailable or disabled classifier leaves
  these cases `UNSURE`; budgets and cooldowns are unchanged.
- Both semantic and analysis fingerprints include `rental-rules-v2`, so old verdicts
  and templates cannot be reused as current after the rules change. The ordinary
  worker review queue re-evaluates NEW/REVIEWED listings; this is not a database
  backfill or a change to user-selected statuses.

The parser is deliberately conservative and is not a complete natural-language
reasoner. Complex negation, references and custom preferences remain semantic work.

## Regression comparison

Inputs, labels, family splits and all 150 numeric verdicts were checked against the
original exported corpus. The old model reports, raw exports and frozen policies
remain intact. The new numeric-baseline export explicitly removes semantic rules
when evaluating text-free numeric facts.

This is the **already-inspected synthetic challenge set**, used for regression
development, not a fresh blind test or an estimate of production accuracy.
The column below covers the 100-case partition previously called `eval`:

| Measure | Previous rules | Corrected rules |
|---|---:|---:|
| Suitable listings wrongly rejected | 11 / 36 | 0 / 36 |
| Correct rejects / all rejects | 13 / 24 | 9 / 9 |
| Unsuitable listings automatically marked MATCH | 31 / 44 | 0 / 44 |
| Expected-UNSURE cases automatically marked MATCH | 12 / 20 | 0 / 20 |
| Deterministic MATCH | 68 | 0 |
| Deterministic REJECT | 24 | 9 |
| Cases requiring semantic review | 8 | 91 |

All 36 suitable listings are retained as **UNSURE**, not automatically approved.
The nine deterministic rejects consist of six numeric rejects and three text
restrictions. There are no false rejects across the combined 150 synthetic cases;
the 50-case development partition has 14 REJECT and 36 UNSURE results.

The remaining 35 unsuitable examples in the 100-case partition also need semantic
review. This is a safer routing policy, not a standalone classifier meeting the
previous 70% model-coverage gate. No LLM calls were made in this regression run,
so end-to-end decision quality, hosted cost and queue clearance time are unmeasured.
More listings can wait in the queue under the unchanged per-run call budget.

Per-case decisions, reasons, source hashes and metrics are in
[rules-v2-comparison.json](rules-v2-comparison.json). Full exports and the rule-only
run are in the ignored `.decision-benchmark/rules-v2-final-*` artifacts.

python3 tools/decision-benchmark/benchmark.py --backend rules --split eval \
